# 004. Play の内部テストで配り、`v*` タグで GitHub Actions が配信する

- **日付**: 2026-09-10（最終更新 2026-09-27）
- **ステータス**: 採用

## 背景

指定した相手（20人以下）にだけアプリを配りたい。配信手段は Google Play の内部テストにした
（一般には見えない・100人まで・審査待ちが無い）。本番公開はしない（12人を14日間集めるクローズドテストが要り、Data safety フォームも必須になる）。

配るには、Play が受け付けない点を解消する必要があった。

| 当時のビルド | 困ること |
|---|---|
| release を debug 鍵で署名 | Play は debug 鍵を受け付けない |
| `versionCode` が `1` 固定 | Play は同じ番号を二度受け付けない |
| `arm64-v8a` だけをビルド | 32bit・x86_64 の端末で動かない |

`android/` は prebuild の生成物なので、いずれも config plugin から書く必要がある。

また、走行テストで課題が見つかると「直して、すぐ配って、また試す」往復が要る。
手動では毎回、手元のビルド（4〜5分）と Play Console でのアップロードが要る。

## 選択肢

### A. `versionCode` の管理

| 案 | 判断 |
|---|---|
| **A-1. `app.json` の `version` から自動で導出**（`1.34.0` → `13400`） | 採用。上げ忘れの経路が1本になる。各桁は99まで |
| A-2. `versionCode` を手で書く | 却下。`version` と二重管理になる |
| A-3. CI のビルド番号を使う | 却下。手元のビルドで番号が決まらない |

### B. ABI

ローカルのビルド生成物を小さくするため（18.9GB → 3.6GB）、既定は `arm64-v8a` だけにしている（`plugins/withSingleAbi.js`）。

| 案 | 判断 |
|---|---|
| **B-1. 配信用のビルドだけ全 ABI**（環境変数で切り替え） | 採用。切り替えは AAB を作る npm script に埋め込み、人が思い出さなくてよいようにする |
| B-2. 常に全 ABI | 却下。ローカルが再び膨らむ |
| B-3. `arm64-v8a` のまま配る | 却下。配ってから動かない端末に気づく |

AAB の ABI ごとの分割は Play が行うので、全 ABI を入れても利用者のダウンロードは増えない。

### C. 署名鍵（upload key）の置き場

Play App Signing を使うので、自分が持つのは upload key だけ（回復不能な app signing key は Google が持つ）。
upload key は失っても漏れても Play Console で再登録できる（24〜48時間）。

| 案 | 判断 |
|---|---|
| **C-1. 原本は `~/.keystore/`（リポジトリ外）、写しを GitHub の Environment secrets に置き、`v*` タグからの実行だけが読める** | 採用 |
| C-2. 原本を手元だけに置き、手元で署名して AAB だけ上げる | 却下。いちばん重い手元のビルドが残る |
| C-3. 秘密管理サービス（AWS Secrets Manager 等） | 却下。App を AWS に依存させる |
| C-4. 暗号化してリポジトリに入れる（git-crypt 等） | 却下。public リポジトリで暗号鍵の管理が増える |

CI に置いてよいと判断した根拠: 置くのは再登録できる upload key だけで、漏れた鍵だけでは配れない（サービスアカウントの鍵も要る）。
サービスアカウントにはテスト版トラックへのリリースしか与えない。

### D. アップロードの手段

| 案 | 判断 |
|---|---|
| **D-1. `r0adkll/upload-google-play`（コミット SHA で固定）** | 採用。YAML に数行で済む。個人リポジトリのビルド済み JS を実行するので、中身を差し替えられる可変タグは使わない。Google 公式の Action は無く、これが事実上の標準（ワークフローでの利用は約4,000件・作者以外の保守者がいる） |
| D-2. fastlane（`supply`） | 却下。掲載情報やスクリーンショットの一括管理が強みだが、内部テストに AAB を上げるだけなので使わない。Ruby の依存が増える |
| D-3. API を叩くスクリプトを自作 | 却下。書く量が増える |
| D-4. 手動でアップロード | 却下。往復のたびに手作業が要る（初回だけは手動が必須。Play Developer API は既に登録済みのアプリしか更新できない） |
| D-5. AWS の CodeBuild で行う | 却下。Android のビルド環境を用意するのは割に合わず、App を AWS に依存させない |

### E. 引き金

| 案 | 判断 |
|---|---|
| **E-1. `v*` タグの push** | 採用。「`version` を上げたらタグを打つ」規則に乗る |
| E-2. `main` への push | 却下。`versionCode` が同じだと Play に弾かれ、失敗が常態化する |
| E-3. 手動実行のみ | 却下。往復を速くする目的に合わない |

## 決定

- `versionCode` は `version` から config plugin で導出する（A-1）。
- 既定は `arm64-v8a`、配信用ビルドだけ全 ABI（B-1）。
- `v*` タグの push で GitHub Actions（`.github/workflows/play-release.yml`）がビルド・署名し、r0adkll で内部テストへ上げる（C-1・D-1・E-1）。
- 手元のビルド（`npm run bundle:play`）も残す。CI が使えないときの逃げ道にする。

## 影響

- ⚠️ `v*` タグの push は Play への配信を意味する。`version` はビルドが変わるときだけ上げ、上げたら注釈付きタグを打つ。
- ⚠️ public リポジトリなので、ワークフローは `pull_request` では動かさない。
- CI のビルド環境（JDK・Android SDK）を手元と揃える必要がある。
- 手元で署名するときは `App/.env`（gitignore 済み）に鍵のパスとパスワードを書く。手順は `CICD` リポジトリの `PLAY_RELEASE.md` と `SETUP.md`。
- 配る相手には手順書が要る（Google App の既定の解除・API キーの入力・戻り先アプリの選択）。アプリが入っただけでは使えない。
